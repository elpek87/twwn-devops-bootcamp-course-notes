# MONITORING WITH PROMETHEUS

## INTRODUCTION TO MONITORING WITH PROMETHEUS

Prometheus is an open-source monitoring and alerting system designed for collecting and querying time-series data (metrics) from systems, applications, containers and infrastructure. Number one choice for containers and microservices infrastructure.

What is Prometheus used for?

- Constantly monitor all the services
- Alert when service crashes
- Identify problems before they happen

Prometheus architecture:

Prometheus server is built on three main components:

- Time Series Database
- Data Retrieval Worker
- HTTP server to accept PromQL queries

Prometheus can monitor pretty much everything - servers, applications, application servers or databases. These are called **monitoring targets**. Then they divide into units like CPU status, memory usage, request count etc. These that you'd like to monitor are called **metrics**.

Metrics are in human-readable text-bases format. Entries have TYPE and HELP attributes.

**HELP** is the description of what the metric is.

**TYPE** can be one of three types:
- Counter (how many times x happened?)
- Gauge (what is the current value of x now?)
- Histogram (how long or how big something was?)


By default Prometheus pulls metrics from the target's /metrics HTTP endpoints.

Some service provide metrics endpoints by default where for others you'd need an exporter to convert data into metrics and expose them. For containerized apps there are exporters available as Docker images.

There are also many client libraries that allow you to monitor your own applications - expose endpoint and needed metrics on it.

There are two models of collecting metrics - **pull** (Prometheus native) and **push**. Both have its advantages and disadvantages.

Pushgateway is a small service in the Prometheus ecosystem that allows temporary pushing of metrics, which Prometheus can later pull (scrape). It acts as a bridge between PUSH and PULL models.


Configuring Prometheus:

- targets and intervals are defined in prometheus.yaml
- service discovery component is used to find targets and endpoints
- rules are used for aggregating metrics values or creating alerts when condition is met
- prometheus monitors itself
- your own jobs can be defined as well

Alertmanager is a component of the Prometheus ecosystem responsible for handling alerts generated by Prometheus.

Prometheus data storage refers to how Prometheus stores the metrics it collects over time — using its built-in time-series database (TSDB). Storage can be local or remote.

PromQL (Prometheus Query Language) is the query language used in Prometheus to retrieve, filter, and analyze time-series metrics. PromQL can be used in Prometheus Web UI or in Grafana to visualize metrics.

Prometheus characteristics:

- reliable
- stand-alone and self-containing
- works even if other parts of infrastructure are broken
- no extensive set-up needed
- sometimes difficult to scale
- single node is less complex but can be limiting in terms of number of metrics you collect

Prometheus Federation is a technique where one Prometheus server scrapes metrics from another Prometheus server, instead of scraping the original targets directly. This is used in larger setups.

Prometheus is fully compatible with docker and k8s environments.

## INSTALL PROMETHEUS STACK IN KUBERNETES

There are several ways of deploying Prometheus in K8S cluster:

1. Create all YAML configuration files yourself and execute them in the right order - inefficient, lots of effort
2. Using an operator to manage all Prometheus components
3. Using Helm chart to deploy operator - the best way - operator is maintained by Prometheus community.

We're going with the third option:

Helm for initial setup + operator to manage it.

Prometheus community provides Helm Chart repository:

```
$ helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
```

Before installing from the repo it's best to update:

```
$ helm repo update
```
First create separate namespace:

```
$ kubectl create namespace monitoring
```

Install Prometheus:

```
$ helm install monitoring prometheus-community/kube-prometheus-stack -n monitoring
```
To check status of deployment:

```
$ kubectl --namespace monitoring get pods -l "release=monitoring"
```

Prometheus stack on k8s is:

- Prometheus Operator (created Prometheus and AlertManager StatefulSet)
- Grafana
- Kube State Metrics (dependency, scrapes k8s components)
- Node Exporter DaemonSet (runs on each Worker Node of K8S - translates metrics to Prometheus format)

Another interesting parts are:

- multiple configmaps
- CRDs (custom resource definitions)

## INTRODUCTION TO GRAFANA

Another way to visualize the metrics is to use Grafana - an open source visualization and analytics software.

To get admin password for Grafana installed with Helm Chart:

```
$ kubectl get secret --namespace monitoring -l app.kubernetes.io/component=admin-secret -o jsonpath="{.items[0].data.admin-password}" | base64 --decode ; echo
```

Then to access the web UI - port forwarding:

```
kubectl port-forward service/monitoring-grafana -n monitoring 8080:80
```

Core element of Grafana is a dashboard - which basically is a set of one or more panels that visualize your data in multiple forms. Dashboards are highly customizable.

To get data from Prometheus which will later be visualized in Grafana we use PromQL language. Basic knowledge of PromQL is mostly sufficient.

To simulate a spike on the graphs of our K8S cluster:

## ALERT RULES IN PROMETHEUS

Prometheus can alert when some anomaly happens.

Alerting is separated into two parts:

1. Define what we want to be notified about (Alert Rules in Prometheus Server)
2. Send notification (Configure Alertmanager)

There are many alert rules preconfigured in Prometheus from Helm Chart. they use PromQL language to define expressions.

EXAMPLE:

`max_over_time(alertmanager_config_last_reload_successful{container="alertmanager",job="monitoring-kube-prometheus-alertmanager",namespace="monitoring"}[5m]) == 0`

That translates to:

FUNTION(METRIC{FILTERS})[RANGE] == 0

## CREATE OWN ALERT RULES - PART 1 - 3

Alert rules we configure:

1. Alert when CPU > 50%
2. When Pod cannot start


When using Prometheus Operator we can define custom rules by Custom Kubernetes Components defined by CRDs. If it wasn't like that we would have to add custom rules to rule files from Prometheus configuration and reload Prometheus manually.

Prometheus Operator extends Kubernetes API and lets us create custom K8S resources. Operator takes custom resource and tells Prometheus tp reload the alert rules.

Labels are important in rules definitions to be picked up.

To create rule:

```
$ kubectl apply -f alert-rules.yaml
```

To verify:

```
kubectl get PrometheusRule -n monitoring | grep main-rules
```

It will appear in Prometheus Rules after a while - after reload gets triggered.

To verify if it was actually reloaded:

```
$ kubectl logs prometheus-monitoring-kube-prometheus-prometheus-0 -n monitoring -c config-reloader
```

To simulate CPU spike we take an image from DockerHub and run it in our K8S cluster:

```
$ kubectl run cpu-test --image=containerstack/cpustress -- --cpu 4 --timeout 30s --metrics-brief
```

## INTRODUCTION TO ALERT MANAGER

When the Alert Rule gets fired - Alertmanager gets notified. Alertmanager then sends notifications to the end users.

Main part of the Alertmanager configuration is the "recievers" attribute.

Receivers are basically the notification channels - smtp, telegram, pagerduty etc. It operates on labels to route where (which receiver) send the notifications.

The "inhibit_rules" allows you to suppress notifications for certain alerts when other related alerts are firing already.
